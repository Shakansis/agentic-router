# v0.9.12 coordination decisions

## Invariants

- Execute resolves the selected target before it evaluates the resident coordinator.
- A resident is not a prerequisite for a target with approved direct coordination evidence.
- Conformance is evidence for one exact path and identity; failure on one path does not fail another path.
- The Host remains the sole authority for plan identity, validation, approval, execution, retry budgets, cancellation, persistence, and terminal state.
- A deterministic protocol failure disables that exact path for the current turn. It is never retried with the same prompt, schema, and protocol.
- A semantic proposal failure may receive one Host-authored correction containing the rejected field or contract, its reason, and the expected shape. Repetition changes strategy.
- Structured coordination proposes one action at a time. A later action is requested only after the previous Host result is available.

## Additive conformance contract

Conformance evidence is keyed by provider, exact model identifier, provider revision or local digest, provider-adapter version, Ollama version when applicable, benchmark-contract version, and coordination profile.

The supported profiles are `native-strict`, `native-adaptive`, `structured-action`, `guidance-only`, `failed`, and `unknown`. Negative evidence remains visible and scoped to its profile. Existing `passed`, `model`, `digest`, `ollamaVersion`, and `failure` fields remain compatible; profile and identity fields are additive.

## Arbitration

The Host evaluates paths in this order:

1. approved target `native-strict`;
2. approved target `structured-action`;
3. bounded specialist guidance with an eligible resident bridge;
4. typed blocked result after all compatible and budgeted paths are exhausted.

The activity stream reports the selected target, effective coordinator, configured resident, execution path, conformance identity, and handoff reason separately.

Resident bridge eligibility accepts independently approved `native-strict` or
`native-adaptive` evidence. The adaptive benchmark supplies a rejected prior
tool call plus exact Host feedback and requires one corrected native call. An
empty required field remains invalid; strict failure is preserved as negative
evidence instead of being converted to approval.

## Structured actions and plan identity

The specialist returns an objective, a normalizable action title, a registered tool name, and a JSON arguments object. It does not assign plan or step IDs. The Host creates or revises the visible plan and generates stable IDs before it validates the proposed action.

## Deterministic tool-name normalization

Native tool calls and structured specialist guidance use one Host-owned closed
registry. Canonical and alias dictionaries use `StringComparer.OrdinalIgnoreCase`;
the registry validates canonical identifiers, alias targets, canonical
collisions, and case-insensitive alias collisions during construction.

Resolution changes only the tool name. It preserves the original name and
resolution source, verifies that the canonical tool is offered in the current
phase, and then runs the unchanged argument, path, policy, approval, stale-write,
and execution validation. Unknown and deliberately ambiguous aliases are
rejected. No fuzzy matching, edit distance, embeddings, model inference, or
argument normalization is permitted.

## Resident and memory evidence

Resident eligibility combines path conformance with the configured context and memory headroom policy. Exact runtime or measured-profile evidence is preferred. Metadata-only conclusions remain labelled estimates. A local specialist may temporarily evict a different resident only through the bounded lifecycle service, with absence verified and restoration attempted after success, cancellation, or failure.

## Permission boundary

Deterministic fake-provider E2E validation does not use the GPU or cloud quota. Any real Ollama generation, benchmark, smoke, or memory measurement requires explicit permission immediately before the run. Real cloud conformance or validation requires separate permission.

## Pending approval revision

A user may revise only the editable argument surface of a pending
`run_process`, `git_stage_files`, or `git_unstage_files` action. The revision
keeps the Host-generated action ID and canonical tool fixed. Process text is
parsed into executable plus argument tokens without invoking a shell; Git paths
are one repository-relative path per line. The Host runs the normal process or
Git validation again before atomically replacing the pending action.

The approval decision and revision share a serialized pending-action gate. A
revision from another browser/execution session, a revision after a decision,
or a policy-invalid revision is rejected and never executed. Once a decision
is accepted, the browser removes decision controls and renders the authoritative
execution result as a collapsed child of the same approval card.
