Which profile applies?

Chat uses the intent classified for the current request. A manual model choice changes the model, not the intent's inference profile. Execute uses the Supervisor profile only for Supervisor turns, including when Auto selects supervision. Workers use the configured profile for their active work item, independently of the Supervisor. Direct Execute uses the current intent's configured inference profile, including when Auto starts directly. A manual model choice does not replace the configured sampling settings.

These settings are saved with the use profile, not with a model. The same profile can therefore be used with Qwen, Gemma, or a cloud model. A provider or model may accept only some controls.

Basic controls

Temperature
Controls variation in the next token choice. Lower values tend toward the most likely wording; higher values allow more variation. Zero does not guarantee identical full answers across models, tools, or changing context.
Thinking
Controls whether and how much a compatible model reasons before answering. Auto sends no profile override and leaves the provider or model behavior in place. Disabled and Enabled toggle reasoning where supported; Low, Medium, High, and Max request a level. Available choices depend on the selected model and adapter. For Supervisor turns, Effort by supervised phase controls Plan, Verify, Complete, and Recovery; the Supervisor profile's Thinking field is inactive. Direct Execute and Workers use Thinking from their task inference profile. The legacy Work phase setting is retained for configuration compatibility and no longer controls Worker inference.

Context and output for Ollama

Set these values under Runtime and memory → Ollama context profiles. They belong to the Ollama execution role and its optional model override, independently of the inference profile. A model can therefore use one sampling profile while the Host applies the context profile for its actual role.

Minimum, target, and maximum context
The context window contains both input and generated output. The Host normally requests the target and can increase it when more space is required, up to the configured maximum and the model's declared limit. Minimum is the lowest allowed window for that role.
Output limit
The role's ceiling for one model response. The Runtime and memory response reserve and task-specific budgets may request a smaller amount. Multi-step Execute work can make several model calls; this is not a total task limit.
Keep-alive
How long Ollama should keep the model loaded after a request. It affects residency, not answer style.

Advanced controls

Top P
Limits the candidate tokens by their combined probability. A lower value narrows the choices. Changing it together with temperature can make the result harder to predict.
Top K
Limits the number of candidate tokens considered at each step. A lower number narrows the choices. Some providers do not offer this control.
Min P
Filters candidates that are too unlikely relative to the leading token. Larger values filter more choices. Some providers do not offer this control.
Repeat penalty
Discourages repeating tokens. One is neutral; higher values can reduce repetition but may hurt names, code, or repeated structure.
Repetition window
How many recent tokens the repeat penalty examines. Zero disables the lookback; -1 uses the full context. Leave it blank to use the provider default. This control is currently available through the Ollama adapter.
Seed
A fixed integer requests a repeatable sampling path with the same model, prompt, and settings. Auto generates a fresh positive integer for each run and sends it when the provider accepts seeds. The requested value is recorded beside the run identity; providers without seed support are reported as unavailable. A provider may not guarantee identical output even with the same seed.

Blank optional fields leave that choice to the provider and existing runtime configuration. Start with one adjustment at a time and inspect the output.

KV cache: memory, precision and speed

The KV cache retains attention state for tokens in the context. Its format is independent of the model weights: a Q4_K_M model can use an F16 cache. Changing cache precision does not change the configured context window.

OptionTrade-off
AutoInherit the Ollama server environment. It may already select a quantized cache; Auto does not mean F16 is confirmed.
F1616-bit floating-point cache. Uses more memory and avoids additional cache quantization. A useful accuracy and performance baseline when the intended context fits.
Q8_08-bit quantized cache, roughly half the F16 cache memory with some precision loss. Useful when cache memory limits the desired context.
Q4_04-bit quantized cache, roughly one quarter of the F16 cache memory with greater precision loss. Check answer quality and throughput on your actual workload, especially at long context.

These savings concern cache tensors, not total model memory. Weights, compute buffers, recurrent state and backend overhead still occupy memory. Quantized cache requires Flash Attention in Ollama.

Smaller is not necessarily faster. Cache conversion, backend kernels and speculative decoding acceptance can change throughput. Compare the same prompt, model, context, sampling and draft depth; also check quality. Draft acceptance is accepted draft tokens divided by proposed draft tokens, not accepted tokens divided by all output tokens.

Select KV cache precision in Performance by model, or inherit the global managed Ollama default. The exact model and digest share this configuration across roles and harnesses. Use the Settings footer Save; the next request selects a compatible AR-owned server without restarting another cache configuration. Different precisions use separate server processes and can retain loaded models until their keep-alive expires or they are unloaded. Quantized cache enables Flash Attention for that process. External Ollama and cloud providers retain their own configuration. AR does not change Windows environment variables. Server configuration is reported separately from verified runner activation.

Keep the context at your real target during comparisons. A 128K window means a capacity of 131,072 tokens; it does not imply that each test prompt fills that window. Check the runner configuration and measured tokens/s rather than treating a saved setting as proof of activation.

Provider and harness support

The Settings page shows what the configured model's adapter can send. Ollama accepts the sampling controls listed here. The current Groq, Cerebras, and Google AI Studio adapters send temperature and Top P. Their adapters do not send Top K, Min P, repeat penalty, or repetition window. A specific model may still reject a supported adapter field; its provider error is shown in the turn activity.

Harness-native Execute paths have their own runtime contracts. A sampling control is applied only when that harness can receive it; unavailable controls are reported in activity. Saving a profile does not silently reconfigure a model or provider.
