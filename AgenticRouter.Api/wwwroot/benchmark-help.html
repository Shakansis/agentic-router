Quick start

  1. Select installed local models, available harnesses and test suites. A harness is the runtime that drives the model and its tools. Each model and harness pairing is a separate combination.
  2. Choose timeout, context window, repetition count and Default GPU. The GPU starts with the Settings selection and can be changed for this benchmark.
  3. Select Run benchmark. This starts real execution using the selected models. Tests use dedicated benchmark workspaces.
  4. In Tests in progress, select a combination or use Previous, Next or View active test. Expand a test for its outcome and activity timeline; open Advanced details for comparisons and recorded checks.
  5. In Results, inspect failures before comparing scores. Use Recommendation for guidance across saved runs and History and comparison for changes over time.

Model × Harness combinations run sequentially. Closing the benchmark view or disconnecting the browser does not cancel the active run. Use Cancel to request cancellation; completed evidence remains available.

Controls and configuration

Models / Harnesses / Tests
Switches define the run matrix and suites. Availability and versions help distinguish missing runtimes from failed tests. Experimental harness labels describe integration maturity.
Per-test timeout (seconds)
Time allowed for a test, within the UI's 5–1600 second range. Scenario-specific limits may also apply. Timeouts are recorded; independent subsequent combinations can continue.
Sequential runs
Repeat the full selection 1–20 times. Each repetition has its own run ID and saved evidence; results are not collapsed into one average run.
Context window (tokens)
Requested model context, from 4096 to 131072 tokens. The runtime evidence distinguishes requested context from observed context; selecting a value does not prove it was observed by the backend.
Default GPU
Starts with the selection in Settings. Changing it affects only this benchmark and is frozen when the run starts; explicit model GPU affinity takes precedence. Saved selection and actual backend placement are different evidence.
Scoring profile / Score weights
Default or custom weights determine calculated scores. Each weight is 0–100 and at least one must be positive. Their sum is the normalization denominator; it need not be 100. Editing weights rescores existing evidence without model execution. Reset restores defaults.
Custom Benchmark Prompt / Run name
The custom test sends your exact prompt; the optional name helps identify it in history. Inspect the output and workspace, then assign a quality score and review notes. Execution completion does not automatically validate arbitrary user goals.
Progress, finished, passed and terminality
Finished counts tests that reached an ending, including failures. Passed counts accepted predefined tests. Terminality measures whether execution reached a recognized ending; it is not a correctness or pass rate.
Results, matrix and ranking scope
Select a pair to inspect its tests. Model and harness views aggregate across combinations in the selected run. The matrix shows individual cells, including unavailable and interrupted combinations.
Workspace review / Download / Rerun
Where available, inspect retained generated files or download the workspace. Rerun starts new execution and evidence; it does not repair or overwrite the earlier measurement.

What each test checks

The canonical prompt and recorded validation facts are available in Advanced details. Fixed tests check exact outcomes and, for some scenarios, specific observable actions.

TestAcceptance intent
FS-CREATE-001Create a file at the exact expected location with exact UTF-8 content. Preserve unrelated files.
FS-READ-001Read two fixture files and return their required facts without modifying the workspace. The validator can use observed reads or required facts in the report.
FS-UPDATE-001Apply the specified edit and preserve all other content and files.
FS-DELETE-001Delete only the requested target and preserve unrelated files.
CONTINUITY-001Preserve accumulated requirements across three completed turns in the same harness session.
SCOPE-RETENTION-001Make a narrow edit without recreating the target or changing neighboring files.
RECOVERY-001Attempt the stale path once, surface the failure, read the correct path and produce the exact recovery output. The Host must recognize the required read evidence and recovery.
CONVERGENCE-001Make the edit, validate once and stop, with the required final report. When tool trace evidence is available, require exactly one recognized post-edit validation read and no later tool calls.
TERMINALITY-001Finish the required edit and truthfully disclose that optional process validation is unavailable. A permitted partial terminal result can be accepted.
STALE-CONFLICT-001Preserve an external file change made by the Host between turns, apply the requested edit and report preservation.
TRUTHFUL-REPORT-001Complete the required edit, attempt the absent optional validation file once and report its failure truthfully. Do not claim that everything passed.
MISSING-GAME-001Real Life Problem: produce the missing Snake game, preserve existing files, complete Execute and pass the Host's browser checks. Browser evidence covers the implemented checks, not every aspect of game quality.
MANUAL-CUSTOM-001Custom Prompt: execute your task and retain reviewable evidence. You assign quality; this test is excluded from automatic predefined scoring and recommendations.

Read the outcome first

Passed / All tests passed
Passed means that test satisfied its acceptance criteria. “All tests passed” appears only when every planned test for the inspected combination is present and passed. A cancelled, incomplete or manually reviewed run does not qualify.
Failed / Host validation: fail
The Host could not confirm all required acceptance criteria. This is not a claim that the Host process crashed. Files can be correct while required behavioral evidence is missing.
Error / timed out / cancelled / unavailable
Execution or validation did not finish normally, exceeded its time limit, was cancelled or lacked a required runtime or validation capability. Inspect the typed error and phase for the actual cause.
Pending review / reviewed
Custom Prompt quality is assessed by you. Its user ranking is separate from predefined test rankings.

Missing evidence is not proof that an action never happened. For example, native tool activity may lack the canonical tool name or exact path the benchmark expects. “The Host could not confirm the read” describes that limitation. A “tool completed” event alone does not prove the whole test passed.

Successful tests do not add explanation text. Failed tests show only relevant recorded failures, with a general fallback for older or incomplete evidence. Advanced details retains technical facts and errors. The final harness report is the agent's narrative; Host checks determine acceptance.

In comparison tables, Match means the displayed expected and observed values are equal; Different means they differ. This does not replace the test's acceptance result. Recorded identifies supporting evidence that is not directly comparable, such as a list of changed files beside an expected target path. Not observed preserves missing evidence. Hashes have Copy buttons; wide tables scroll horizontally and can be focused with the keyboard. Saved tool timelines show the last eight recorded events; complete traces remain in raw evidence.

How ranking works

A score is not a pass rate. A failed test may earn points for a correct file or successful termination while failing another required criterion. A high score does not turn that failure into a pass.

Dimension · default weightCalculation
Objective success · 35100 if the objective was achieved; otherwise 0.
Correctness / exactness · 25Mean of exactness and available continuity, recovery and truthful-report metrics.
Terminality · 15Recorded behavioral terminality; otherwise 100 for completed execution and 0 for other endings. Behavioral terminality can include recognized failure endings.
Workspace accuracy · 20Mean of recorded containment accuracy and available scope and hygiene metrics. These include expected file-change scope, not only security boundaries.
Efficiency · 5Mean of a tool-call score and available convergence. Unknown call count = 50; zero = 80; one = 100; two = 90; three = 75; four = 60; then subtract 10 per call down to 20. This is not a speed benchmark.

Test score = sum of (dimension × weight) divided by total weights, rounded to two decimals. Pair score sums recorded predefined scores and divides by the planned predefined test count; missing tests do not inflate it. Model/harness aggregates average their matrix cells.

Ranking sorts by score descending, then passed count descending, duration ascending, and stable model/harness identifiers. Live rankings are provisional. Custom Prompt rankings use user scores separately. Editing weights changes the projection, not the original evidence or acceptance result.

Recommendations and confidence

The recommendation uses saved local evidence, so it can differ from the currently displayed run ranking. “View overall recommendation” does not launch a benchmark. Evidence links identify the supporting runs; alternatives and trace explain the calculation.

Category
General coding uses the active score. Other categories blend 80% category focus with 20% active score: exact filesystem focuses on correctness/workspace/hygiene (55/35/10); long continuity on continuity/terminality/correctness (50/30/20); recovery-heavy on recovery/terminality/correctness (50/30/20). Correctness-first, terminality-first and efficiency-first emphasize that dimension. Missing focus metrics are omitted and remaining weights normalized.
Current and historical evidence
The newest relevant evidence anchors each candidate. With comparable history, current evidence contributes 70% and comparable history 30%. Otherwise, partially comparable history contributes 10% and current evidence 90%. Incompatible history contributes no score.
Confidence
Limited: no comparable historical observations. Moderate: one. Strong: at least two. Mixed: contributing scores differ by at least 20 points. Insufficient evidence means no usable recommendation. Confidence is evidence coverage and consistency, not a probability of future success.
Scoring
Choose the active profile or default profile for the recommendation.
Research external evidence
Explicitly requests external research through configured search. External claims remain unverified external evidence, distinct from local measurements; they do not substitute for local benchmark validation.

How results affect Agentic Router

Benchmarking does not train a model, modify its weights or grant extra capabilities. It creates local evidence used by recommendations and automatic harness selection.

When Auto harness routing applies to a selected local model, AR first looks for the best usable ranked available harness for that exact model. If none exists, it can use aggregate harness scores across ranked models. Without usable evidence, available Native is the deterministic fallback. The model selection is preserved.

The route is retained during the active task session. New results do not cause a mid-session switch. Manual selections remain explicit choices. Host approvals, workspace boundaries and validation remain authoritative regardless of ranking.

History and comparison

Choose a saved result, filter by model, harness or suite, then select a baseline and candidate for comparison. Compare suite, test/fixture/acceptance versions, environment and identities before interpreting score or duration deltas.

Comparable
Evidence supports direct comparison under the recorded compatibility checks.
Partially comparable
Some dimensions match; read the listed differences before drawing conclusions.
Not directly comparable
Do not interpret score differences as a measured improvement of the same setup.
Original / recalculated score
Original weights belong to the saved run. Recalculated values apply the selected profile to that same evidence without rerunning inference.
Delete selected / Delete all
Removes saved benchmark results as requested. Removing history also removes that evidence from future recommendation calculations. Keep evidence you want to compare later.

Advanced evidence glossary

Unavailable means the value was not observed or supplied; it is not zero. Measured, detected, estimated, requested and observed values are different kinds of evidence. Raw evidence retains original field names and values.

Terminal / Failure category / Error
The execution ending, failure classification and typed code/message. These explain runtime outcomes separately from Host acceptance.
Host validation / Workspace containment / Workspace
Acceptance result versus recorded workspace accuracy. The historical “Workspace containment” label includes file-change scope checks: a failure does not on its own establish a security escape. PASS can coexist with failed behavioral checks.
Exactness / Byte, directory and filename accuracy
Match against expected content, bytes and location. Hashes and byte lengths expose exact comparisons, including newline differences.
Scope accuracy / Hygiene / Changed files / Unexpected
Whether only expected files changed and unnecessary artifacts were avoided. Unexpected can include missing: entries for expected changes that were not found. scopeAccurate and missingExpectedChanges explain the behavioral scope check.
Continuity / Recovery / Convergence / Truthful report / Narration
Scenario metrics for retaining requirements, recovering from a tool failure, stopping after success and reporting observed reality. Narration is accurate, incomplete or misleading. Non-applicable metrics remain unavailable.
Turns / Terminal turns / Turn budget / Scenario timeout / Acceptance version
Recorded successful versus planned turns, allowed scenario turn count, time budget and version of the acceptance rules. A completed tool call is not a completed turn or accepted test.
Tool calls / Errors / Recovered
Observed tool attempts, surfaced failures and successful recovery observations. A designed failure can be required for a passing recovery test.
Stale read attempts / Correct read observed
staleReadAttempts must be one and correctReadObserved true in RECOVERY-001. These are recognized canonical reads with matching paths; native activity without matching evidence may not count.
Tool trace available / Post mutation validation reads / Tool calls after success / Final report matched
For CONVERGENCE-001: availability of semantic trace, recognized reads after the last edit, later actions and expected report text. With trace available, require one validation read and zero later calls.
Target exact / Target recreated / Changed path count
SCOPE-RETENTION-001 checks final content and whether the trace shows recreation. The change count helps identify edits outside the target.
Expected / Actual final state / External mutation recorded / Initial read observed / External change preserved
Continuity and stale-conflict diagnostics. The external mutation is the Host's deliberate between-turn edit. Initial-read evidence is diagnostic; not every displayed fact is an independent pass condition.
Required change observed / Optional capability / Truthful report / Optional read attempts / Optional failure observed
Terminality and truthful-report facts distinguish required file work from intentionally unavailable or failed optional checks. TRUTHFUL-REPORT-001 requires one observed optional read and a surfaced failure.
Expected path / Absent path / SHA256 / Byte length / Primary and secondary read / Read evidence / Deleted files
CRUD diagnostics describe exact file content and location, source facts, observed-read versus report evidence and actual deletion scope. “Missing” is distinct from an empty file.
Existing files unchanged / Snake created / Unrelated files created / Browser validation / Browser errors / Referenced scripts and styles
Real Life Problem diagnostics cover preserved fixtures, game output, browser resources and errors. Observation milliseconds is browser observation time, not model execution duration. The canonical validator determines which diagnostics gate acceptance.
Runtime · GPU selection / Backend / Processor / Context
Configured device choice versus observed backend/processor and requested versus observed context. Unobserved placement must not be inferred from the selection alone.
Runtime · Model / VRAM / RAM / Memory samples
Reported residency sizes, estimated RAM and device/system snapshots. Samples do not necessarily represent peak usage or memory attributable only to this run.
Runtime · Prompt and output tokens/s / Timeout phase / Last progress
Available provider throughput and the latest observed execution phase. Unavailable throughput is not zero throughput.
Operational · Strategy / Tool validation errors / Repeated calls / Recovery attempts / Execution turns
Requested and resolved execution strategies, invalid tool requests, repeated actions and recovery observations. These diagnostics help explain behavior without changing acceptance.
Duration / Execute duration / Host setup / Browser validation duration
Overall test timing and available phase timings. Do not treat every duration as model inference time.
Tokens / Provenance / Unavailable metrics
Input/output counts and their source. Missing counts stay unavailable; estimates are not exact provider usage. Local Ollama has no per-token provider charge.
Workspace ID / Fixture fingerprint / Workspace cleaned / Run ID
Identities, fixture-content fingerprint and cleanup evidence. Cleanup reports workspace lifecycle, not success of the task. Retained reviewable workspaces are separate from disposable scenarios.
Canonical prompt / Final harness report / Persisted turns / Host events / Raw evidence
Exact input; agent narrative; recorded turn outcomes; Host-originated activity such as external mutations; and the original structured record. Narrative never overrides Host facts.
